# Автоматический захват новых закупок из сохранённого ключа TenderPlan

**Дата:** 2026-09-13

**Статус:** согласованный дизайн, реализация не начата

**Ветка:** `codex/tenderplan-saved-search-intake`

## 1. Цель

Каждые 10 минут проверять один сохранённый ключ TenderPlan и автоматически
запускать существующий агентский анализ только для закупок, которые впервые
появились в выдаче после включения автоматизации.

Закупки, уже находящиеся в сохранённом ключе во время первоначальной
инициализации, не анализируются.

После обнаружения новой закупки используется существующая цепочка:

```text
TenderPlan saved key
→ Intake Resume
→ TenderPlan Orchestrator
→ Подготовка документов
→ Агентский анализ Codex
→ 27 итоговых результатов
→ Финализация
→ PDF-отчёт
```

## 2. Проверенное текущее состояние

Read-only проверка live n8n от 2026-09-13 подтвердила:

- `[CODEX CANDIDATE] TENDER — TenderPlan Mark Intake` активен;
- расписание уже выполняется раз в 10 минут;
- workflow получает закупки по метке через
  `GET /api/tenders/v2/getlist?type=1&id=<mark_id>`;
- каждая найденная закупка передаётся в активный `Intake Resume`;
- `Intake Resume` использует `source_event_key` и таблицу
  `tender_analysis_intake_events` для идемпотентной обработки событий;
- дополнительная защита не создаёт второй незавершённый или уже завершённый
  `analysis_run` для того же `tender_id`.

Текущая repository-документация оркестратора описывает более старый ручной вход
и не полностью соответствует live n8n. Для этой спецификации фактическим
источником текущего поведения считается live workflow.

## 3. TenderPlan API

Официальная документация TenderPlan определяет для
`GET /api/tenders/v2/getlist` следующие режимы:

- `type=0` — получить закупки по сохранённому ключу;
- `type=1` — получить закупки по метке;
- `id` — идентификатор соответствующего ключа или метки;
- `page` — номер страницы выдачи.

Метод требует право `relations:read`.

Получение списка сохранённых ключей через `GET /api/keys/getall` требует
`keys:read`. Оно нужно только для автоматического поиска ID ключа по названию.
Если ID сохранённого ключа известен заранее, runtime использует только
`relations:read`.

Механизм TenderPlan Cursor API не используется: он помечен deprecated и не
поддерживает фильтрацию непосредственно по сохранённому пользовательскому
ключу.

Официальная документация: <https://tenderplan.ru/api/doc/>.

## 4. Выбранный подход

Создать отдельный небольшой входной workflow и сохранить существующий вход по
метке без изменений.

Рабочее техническое название:

```text
TENDER — TenderPlan Saved Key Intake
```

Человекопонятное назначение:

```text
Получение новых закупок из сохранённого поиска TenderPlan
```

Такой вариант:

- не смешивает ручную метку и автоматический поиск;
- не меняет основную цепочку анализа;
- использует существующие механизмы идемпотентности;
- позволяет независимо отключить автоматический поиск;
- оставляет полный audit trail обнаружения закупки.

## 5. Первый запуск и момент включения

### 5.1. Определение момента включения

Автоматизация считается включённой после успешного завершения первоначальной
инициализации и появления baseline marker в PostgreSQL.

Это устраняет неоднозначность для закупок, которые появляются во время
первоначального чтения нескольких страниц TenderPlan.

### 5.2. Порядок первоначальной инициализации

Новый workflow сначала остаётся неактивным и один раз запускается вручную.

Он должен:

1. Получить все страницы выдачи сохранённого ключа.
2. Проверить структуру всех ответов.
3. Собрать уникальные `tender_id`.
4. Одной атомарной DB-операцией зарегистрировать их как baseline-события со
   статусом `completed` и действием `baseline_existing_skipped`.
5. В той же операции создать baseline marker для выбранного ключа.
6. Вернуть количество закупок, сохранённых в baseline.
7. Не вызывать `Intake Resume` и не создавать `analysis_run`.

Если не удалось получить хотя бы одну страницу или проверить ответ, DB-операция
не выполняется и baseline marker не создаётся.

После проверки результата первоначального запуска workflow активируется по
расписанию.

### 5.3. Идентификаторы baseline

Для baseline и рабочих событий используется существующая таблица
`tender_analysis_intake_events`. Новая таблица не создаётся.

Baseline marker:

```text
source = tenderplan
event_key = tenderplan:key:<saved_key_id>:baseline:v1
event_type = key_baseline_completed
status = completed
action = baseline_initialized
```

Baseline-событие конкретной закупки использует тот же event key, который позже
использовался бы для её запуска:

```text
tenderplan:key:<saved_key_id>:tender:<tender_id>
```

Поэтому закупка из первоначального списка не сможет случайно перейти в анализ
после перезапуска или повторной инициализации.

## 6. Регулярная проверка

После инициализации workflow каждые 10 минут выполняет:

1. Читает baseline marker.
2. Получает все страницы выдачи ключа с параметрами:

   ```text
   type = 0
   id = <saved_key_id>
   page = 0, 1, 2, ...
   ```

3. Завершает пагинацию только после корректного признака конца выдачи.
4. Проверяет, что каждый найденный объект содержит корректный `tender_id`.
5. Удаляет дубли `tender_id` внутри ответа.
6. Одним запросом получает уже зарегистрированные event keys.
7. Передаёт в `Intake Resume` только отсутствующие в журнале закупки.

Чтение всех страниц обязательно. Частичная выдача не должна приводить к
обновлению состояния или запуску части найденных закупок.

До runtime-подтверждения фактической сортировки TenderPlan запрещено
останавливать пагинацию после первой уже известной закупки: такой алгоритм может
пропустить новые элементы на последующих страницах.

Пагинация имеет конечный защитный предел. Достижение предела является ошибкой,
а не успешным частичным результатом. Точное значение определяется после
read-only probe реального сохранённого ключа.

## 7. Контракт передачи в Intake Resume

Для каждой новой закупки передаётся:

```json
{
  "trigger_kind": "tenderplan_key",
  "source_event_key": "tenderplan:key:<saved_key_id>:tender:<tender_id>",
  "tender_id": "<tender_id>",
  "analysis_run_id": "",
  "manual_override": false,
  "observed_at": "<ISO-8601 timestamp with timezone>"
}
```

Вызов выполняется отдельно для каждой закупки, без ожидания завершения полного
анализа.

## 8. Минимальное изменение Intake Resume

`Intake Resume` должен принять новый `trigger_kind = tenderplan_key`.

### 8.1. `Validate Intake Input`

Для `tenderplan_key` действуют те же identity-ограничения, что для
`tenderplan_mark`:

- `tender_id` обязателен;
- `analysis_run_id` запрещён;
- `manual_override` должен быть `false`;
- `intent = automatic`;
- `run_authoritative = false`;
- `source = tenderplan`.

### 8.2. `Prepare Event Identity`

Добавляется отображение:

```text
trigger_kind = tenderplan_key
→ source = tenderplan
→ event_type = key_match_added
```

Остальная логика `Intake Resume` не меняется.

## 9. Защита от повторов

Используются два уже существующих уровня защиты.

### 9.1. Уровень события

Уникальная пара `(source, event_key)` в
`tender_analysis_intake_events` гарантирует, что одна закупка одного сохранённого
ключа будет принята только один раз.

### 9.2. Уровень запуска

`Resolve TenderPlan Runs` проверяет существующие запуски по сочетанию:

```text
source = tenderplan
tender_id = <tender_id>
```

Если закупка ранее уже анализировалась через метку, второй `analysis_run` не
создаётся, даже если событие сохранённого ключа имеет другой event key.

Новый parser, validator или field-specific rule для этой функции не требуется.

## 10. Ошибки и восстановление

### TenderPlan временно недоступен

Execution завершается ошибкой без записи baseline или частичного набора
событий. Следующий плановый цикл снова читает полный список.

### Ответ имеет неизвестную структуру

Workflow завершается ошибкой. Неизвестный объект не пропускается молча.

### Ошибка одной страницы

Ни одна закупка из текущего цикла не передаётся дальше. Следующий цикл повторяет
полное чтение.

### HTTP 429

HTTP Request применяет ограниченный retry с задержкой. Если попытки исчерпаны,
execution завершается ошибкой и восстанавливается следующим циклом.

### Повторный или пересекающийся schedule execution

Оба execution могут увидеть один и тот же новый `tender_id`, но только один
сможет успешно claim-нуть уникальный intake event. Второй получает безопасный
no-op.

### Постоянная ошибка доступа

Ошибка не подавляется и видна как failed execution n8n. Внешнее уведомление об
ошибках не входит в эту задачу и подключается к общему каналу мониторинга после
выбора канала доставки.

## 11. Credentials и конфигурация

TenderPlan access token остаётся в существующем n8n Credential типа Header Auth.
Токен не хранится:

- в Code Node;
- в Set Node;
- в workflow JSON;
- в repository;
- в n8n Variables.

`saved_key_id` не является секретом. Для MVP с одним ключом он задаётся как
явная конфигурация workflow. Имя ключа также сохраняется в заметке workflow,
чтобы оператор понимал, какой поиск подключён.

Перед реализацией проверяется, что credential имеет `relations:read`. Если ID
ключа нужно получить по названию через API, отдельно проверяется `keys:read`.

## 13. Проверки

### Offline

1. Первый запуск при 50 существующих закупках создаёт baseline из 50 элементов
   и 0 анализов.
2. Повторная инициализация не меняет baseline и создаёт 0 анализов.
3. После baseline появляется один новый `tender_id` — формируется один входной
   объект `tenderplan_key`.
4. Следующий poll с тем же списком не формирует новый объект.
5. Несколько новых закупок формируют по одному объекту на каждую.
6. Дубли одной закупки на разных страницах схлопываются.
7. Неверный `tender_id` останавливает цикл.
8. Ошибка промежуточной страницы не допускает частичного dispatch.
9. Новый event key устойчив к повторному исполнению.
10. `Intake Resume` принимает `tenderplan_key` и отклоняет несовместимые identity
    поля.

### Runtime canary

1. Выполнить inactive probe реального сохранённого ключа.
2. Зафиксировать структуру ответа, число страниц и критерий завершения
   пагинации.
3. Выполнить ручную baseline-инициализацию.
4. Подтвердить: старые закупки не создали `analysis_run`.
5. Добавить одну контролируемую новую закупку в выдачу ключа либо дождаться её
   естественного появления.
6. Подтвердить один intake event и один analysis run.
7. Повторить poll и подтвердить отсутствие второго run.
8. Только после этого активировать расписание раз в 10 минут.

## 14. Критерии готовности

Функция считается готовой, когда:

- baseline успешно зафиксирован до активации расписания;
- ни одна закупка baseline не получила analysis run;
- новая закупка проходит весь существующий путь до PDF;
- повторные polls не создают дубли;
- ошибка или неполная пагинация не дают частичный dispatch;
- токен TenderPlan отсутствует в export и repository;
- актуальные workflow exports и документация сохранены в проекте;
- runtime evidence первого полного canary зафиксирован.
