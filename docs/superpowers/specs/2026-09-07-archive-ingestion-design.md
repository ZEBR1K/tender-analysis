# Archive ingestion design

**Date:** 2026-09-07

**Status:** согласовано с владельцем проекта; реализация не начата

**Scope:** подготовка вложений TenderPlan перед регистрацией документов и запуском Document Worker, включая безопасную рекурсивную распаковку архивов.

## 1. Цель

Система должна принимать тендер, в котором среди вложений есть архивы, извлекать из них обычные файлы и передавать поддерживаемые документы в существующую цепочку анализа так же, как прямые вложения TenderPlan.

Изменение должно сохранить основные инварианты проекта:

- один `analysis_run` соответствует одному запуску анализа закупки;
- полный набор документов фиксируется до запуска первого Document Worker;
- один Worker обрабатывает один документ;
- PostgreSQL остаётся persistent state и synchronization layer;
- ошибки не замалчиваются;
- происхождение каждого извлечённого файла восстанавливается из audit data;
- число и семантика 27 FINAL-полей не меняются.

## 2. Текущее ограничение

Текущий Orchestrator после получения TenderPlan FullInfo создаёт `analysis_run`, регистрирует исходные вложения и запускает Worker только для расширений PDF, DOCX и XLSX.

Это создаёт две связанные проблемы:

1. архивы не раскрываются, поэтому документы внутри них не участвуют в анализе;
2. неподдерживаемые вложения остаются `pending`, хотя Worker для них не запускается. Текущая readiness-проверка требует равенства числа `completed` и `documents_total`, поэтому такой run может навсегда остаться незавершённым. В `TECH_DEBT.md` это зафиксировано как `OR-0`.

## 3. Принятое архитектурное решение

Добавить отдельный логический этап `TENDER — Подготовить документацию` между созданием `analysis_run` и окончательной регистрацией полного набора документов.

```text
TenderPlan FullInfo
→ нормализация карточки
→ создание analysis_run
→ подготовка документации
   → классификация всех исходных вложений
   → прямой passthrough поддерживаемых обычных файлов
   → скачивание и распаковка только архивов
   → формирование детерминированного ingestion manifest
→ атомарная регистрация полного manifest в PostgreSQL
→ запуск Worker только для pending-документов
```

Через этап подготовки проходят метаданные всех файлов. Бинарное содержимое скачивается на этом этапе только для архивов. Прямые PDF, DOCX и XLSX сохраняют исходный TenderPlan `download_url` и скачиваются позже внутри Document Worker, как сейчас.

Архивы обрабатывает отдельный внутренний Docker-сервис `tender-archive-extractor` на том же сервере. Сервис использует 7-Zip как движок, имеет собственные ограничения ресурсов, не публикует порт наружу и доступен только контейнерам n8n во внутренней Docker-сети.

## 4. Почему выбран отдельный сервис

### 4.1. Выбранный вариант: внутренний сервис с 7-Zip

Преимущества:

- поддержка ZIP, 7Z, RAR и дополнительных форматов одним движком;
- изоляция тяжёлой и потенциально аварийной распаковки от процесса n8n;
- единое место для лимитов, timeout, рекурсии, проверки путей и очистки;
- стабильный внутренний URL для Worker;
- возможность независимо тестировать и заменять реализацию распаковщика.

### 4.2. Встроенная Compression-функция n8n

Не выбрана как основа, потому что её документированный набор форматов не покрывает обязательные 7Z и RAR. Рекурсивная распаковка, хранение артефактов, общий лимит и audit contract всё равно потребовали бы дополнительной логики.

### 4.3. Execute Command внутри n8n

Не выбран, потому что связывает файловую систему и наличие 7-Zip с конкретным n8n main/worker-контейнером. В queue mode команда может выполняться не в том контейнере, где ожидаются файлы; кроме того, Execute Command отключён по умолчанию в новых версиях n8n и увеличивает blast radius процесса автоматизации.

### 4.4. Внешний облачный API

Не выбран из-за передачи тендерной документации третьей стороне, дополнительной авторизации, стоимости и внешней зависимости доступности.

## 5. Поддерживаемые входы

### 5.1. Документы, передаваемые в текущий Worker

MVP не расширяет возможности Document Worker. В обработку направляются:

```text
PDF
DOCX
XLSX
```

Эти типы поддерживаются и как прямые вложения, и как извлечённые файлы.

### 5.2. Архивы

Обязательная поддержка MVP:

```text
ZIP
7Z
RAR
```

Через тот же движок также включаются без отдельной архитектуры:

```text
TAR
GZ
TAR.GZ
TGZ
```

Тип архива определяется не только расширением. После скачивания фактический формат должен соответствовать сигнатуре содержимого. Несовпадение считается ошибкой архива.

### 5.3. Неподдерживаемые обычные файлы

Неподдерживаемый файл не является ошибкой всего анализа. Он регистрируется с terminal-статусом `skipped` и audit-причиной `unsupported_file_type`. Worker для него не запускается.

Если после подготовки не осталось ни одного поддерживаемого документа, run завершается явной ошибкой `NO_PROCESSABLE_DOCUMENTS`, а не зависает в `processing`.

## 6. Рекурсивная распаковка

Архивы внутри архивов распаковываются рекурсивно.

Правило глубины:

```text
исходный архив = уровень 1
архив внутри него = уровень 2
архив внутри второго = уровень 3
архив на уровне 4 = ошибка ARCHIVE_DEPTH_EXCEEDED
```

Каждый архив-контейнер, включая вложенный, остаётся в manifest как audit-запись со статусом `skipped` и причиной `archive_container_expanded`. Поддерживаемые конечные файлы получают `pending`; неподдерживаемые конечные файлы получают `skipped`.

## 7. Рабочая папка и доступ Worker

Под дисковым томом понимается выделенная папка на диске сервера, подключённая к контейнеру распаковщика. Для каждого run создаётся изолированное пространство:

```text
archive workspace
└── analysis_run_id
    └── source_attachment_key
        └── opaque artifact files
```

Исходные имена не используются как физические пути. Сервис назначает непрозрачный `artifact_id`, хранит файл под безопасным именем и возвращает внутренний URL вида:

```text
http://tender-archive-extractor/.../<artifact_id>
```

Worker продолжает получать документ через `download_url`, поэтому его общий контракт скачивания не меняется. Прямой документ использует URL TenderPlan, извлечённый документ — внутренний URL распаковщика.

Папка нужна для двух целей:

- файл переживает отдельный HTTP-вызов и остаётся доступным всем n8n workers;
- transient retry Worker не требует повторной распаковки архива.

После перехода всего run в terminal-статус `completed` или `failed` и при отсутствии документов в `processing` папка run удаляется. Если основной cleanup-вызов не состоялся из-за аварии, сервис удаляет просроченный workspace фоновым TTL-cleanup. Удаление binary не удаляет audit metadata и хеши из PostgreSQL.

## 8. Безопасность распаковки

В этой версии нет антивируса и не закладывается отдельный антивирусный контракт.

Проверка безопасности относится только к механике распаковки. Даже корректный архив может содержать служебное имя, которое пытается записать файл за пределы рабочей папки. Поэтому до и после извлечения блокируются:

- абсолютные Windows/Linux paths;
- UNC paths, drive prefixes и URI-like prefixes;
- сегменты `.` и `..`;
- NUL и другие недопустимые символы пути;
- symbolic links, hard links и специальные filesystem entries;
- коллизии путей после нормализации регистра и Unicode;
- запись или чтение за пределами workspace.

Это не проверка содержания документа и не оценка надёжности тендерной площадки. Это защита файловой системы сервера от некорректной структуры архива.

## 9. Зафиксированные лимиты

Ограничения применяются к каждому исходному архиву вместе со всеми его вложенными архивами:

| Ограничение | Значение |
|---|---:|
| Размер скачанного исходного архива | 100 МБ |
| Размер одного извлечённого файла | 50 МБ |
| Суммарный размер извлечённых данных | 300 МБ |
| Число элементов | 500 |
| Глубина архивов | 3 уровня |
| Полное время подготовки одного исходного архива | 5 минут |

Размеры контролируются во время записи, а не только после завершения распаковки. При достижении лимита операция останавливается, временные результаты не публикуются Worker.

На сервере одновременно выполняется не более одной распаковки. Точные memory/CPU cgroup limits выбираются при deployment-проверке с учётом фактических ресурсов сервера, но отсутствие resource limit не допускается.

## 10. Ingestion manifest

Этап подготовки возвращает JSON manifest версии `tender_document_ingestion_v1`.

Run-level поля:

```text
schema_version
analysis_run_id
source_attachment_count
registered_document_count
processable_document_count
skipped_document_count
archive_count
documents[]
```

Каждый элемент `documents[]` содержит текущие поля регистрации документа и audit metadata:

```text
document_index
file_name
file_extension
display_name
download_url
publication_at
source_size
mime_type
file_size
status
ingestion_metadata
```

`ingestion_metadata` имеет минимальный контракт:

```text
source_attachment_index
artifact_kind
archive_chain
entry_path
archive_depth
content_sha256
extractor_job_id
skip_reason
```

Допустимые `artifact_kind`:

```text
direct_document
archive_container
extracted_document
unsupported_file
```

Для сохранения этого audit trail в `tender_analysis_documents` добавляется `ingestion_metadata jsonb NOT NULL DEFAULT '{}'::jsonb`. Семантика остальных таблиц и 27 полей не меняется.

## 11. Детерминированность и idempotency

Manifest должен быть одинаковым при повторной обработке неизменившегося набора вложений.

- исходные вложения упорядочиваются по позиции в TenderPlan payload;
- содержимое каждого архива упорядочивается по нормализованному полному пути;
- `document_index` назначается только после построения полного упорядоченного manifest;
- `extractor_job_id` детерминирован от `analysis_run_id` и source attachment;
- `artifact_id` непрозрачен, но стабилен внутри job;
- регистрация документов выполняется как idempotent UPSERT по существующему `(analysis_run_id, document_index)`;
- повторный вызов завершённого job возвращает тот же manifest, пока run не очищен.

Два файла с одинаковым basename в разных папках не объединяются. Их `entry_path`, hash и `artifact_id` различаются.

После terminal failure run не возобновляется из очищенного workspace. Повторный пользовательский запуск создаёт новый `analysis_run`.

## 12. Регистрация и запуск Workers

На успешном пути полный manifest регистрируется одной транзакцией:

1. UPSERT всех direct, container, extracted и unsupported records;
2. установка финального `documents_total`;
3. проверка, что число зарегистрированных строк равно `documents_total`;
4. только после commit — dispatch Worker для каждого `pending` документа.

На ошибочном пути Worker не запускается. В PostgreSQL сохраняются:

- все исходные вложения как audit records;
- проблемный архив со статусом `failed` и typed error;
- остальные необработанные исходные вложения как `skipped` с причиной `run_aborted_during_preparation`;
- `analysis_run.status = failed`;
- краткий run-level `error_message` с кодом и source attachment.

Частично извлечённые производные файлы не публикуются и удаляются.

## 13. Readiness semantics

Поскольку archive containers и неподдерживаемые файлы являются terminal `skipped`, readiness должна учитывать их явно.

Run готов к агрегации только когда одновременно выполнено:

```text
registered = documents_total
pending = 0
processing = 0
failed = 0
completed + skipped = documents_total
completed > 0
```

Это изменение закрывает зависание `OR-0`, но не превращает отсутствие поддерживаемых документов в успешный анализ.

## 14. Ошибки и fail-closed behavior

Любая проблема распаковки останавливает весь `analysis_run` до запуска Workers. Основные typed errors:

```text
ARCHIVE_TOO_LARGE
ARCHIVE_FORMAT_MISMATCH
ARCHIVE_ENCRYPTED
ARCHIVE_CORRUPT
ARCHIVE_PATH_UNSAFE
ARCHIVE_ENTRY_LIMIT
ARCHIVE_FILE_TOO_LARGE
ARCHIVE_TOTAL_TOO_LARGE
ARCHIVE_DEPTH_EXCEEDED
ARCHIVE_TIMEOUT
EXTRACTOR_UNAVAILABLE
ARTIFACT_STORE_ERROR
NO_PROCESSABLE_DOCUMENTS
```

Ошибка одного архива не приводит к анализу оставшихся документов. Это исключает ложный `not_found`, сформированный по неполному комплекту тендерной документации.

Сетевые сбои допускают ограниченные transient retries до объявления terminal failure. Повтор не должен дублировать job, документы или файлы.

## 15. Наблюдаемость

В execution и PostgreSQL должны быть доступны:

- `analysis_run_id`;
- source attachment index/name;
- `extractor_job_id`;
- формат и глубина архива;
- compressed и unpacked sizes;
- число entries;
- длительность;
- число pending/skipped документов;
- typed error code и безопасное сообщение без содержимого документов.

Логи не должны содержать binary, credentials, исходные download URLs с чувствительными query parameters или полный текст документов.

## 16. Acceptance criteria

Реализация принимается только после следующих проверок:

1. Тендер без архивов проходит прежний путь без повторного скачивания прямых документов.
2. ZIP, 7Z и RAR с PDF/DOCX/XLSX дают ожидаемые pending-документы.
3. TAR/GZ/TAR.GZ/TGZ проходят тот же контракт выбранного движка.
4. Смешанный архив сохраняет поддерживаемые файлы, а неподдерживаемые помечает `skipped`.
5. Вложенные архивы уровней 1–3 обрабатываются; уровень 4 останавливает run.
6. Повреждённый или зашифрованный архив останавливает run; Workers не запускаются.
7. Каждый из лимитов останавливает run с правильным typed error.
8. Unsafe path, symlink и path collision останавливают run без записи за пределы workspace.
9. Повтор одного job не создаёт дубликатов и возвращает тот же manifest.
10. Одинаковые basename из разных каталогов остаются разными документами.
11. `completed + skipped = documents_total` запускает aggregation ровно один раз при наличии хотя бы одного completed документа.
12. Run без processable documents завершается ошибкой, а не зависает.
13. После terminal run workspace удаляется, а PostgreSQL audit metadata остаётся.
14. Авария сервиса оставляет либо полностью опубликованный manifest, либо terminal failure; частичный набор не попадает в Worker.

## 17. Не входит в scope

- антивирусная проверка;
- OCR или конвертация новых типов документов;
- обработка файлов кроме текущих PDF/DOCX/XLSX в Document Worker;
- изменение semantic pipeline, prompts, facts или 27 FINAL fields;
- публичный endpoint распаковщика;
- хранение распакованных binary после terminal run;
- изменение production n8n или PostgreSQL без отдельного решения о deployment/promotion.
