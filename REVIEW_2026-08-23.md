## 5. Найденные проблемы и риски

### P1 — report stage ещё не реализован

Finalization уже завершает run, но `TENDER — Генерация отчета` — stub. Полный продуктовый MVP пока не закрыт в части Markdown, XLSX и Telegram.

### P1 — legacy/unreachable AI nodes сохраняют старую конфигурацию

В Orchestrator и Aggregator присутствуют физически сохранённые, но unreachable legacy nodes со старым DeepSeek API endpoint/model configuration. Фактический reachable path использует Document Worker/Targeted Recheck и Polza AI. Риск — maintenance drift и ошибочная диагностика; на execution `13852` это не повлияло.

### P2 — документация ранее описывала AG-0 как незавершённый

Старые разделы содержали claims о disconnected Aggregator claim, отсутствии 27/27 barrier и старые E2E-метрики `36 facts / 23 confirmed / 13 rejected`. Они приведены к актуальному snapshot; исторические записи в `DEVELOPMENT_LOG.md` сохранены как история.

### P2 — provider naming в audit metadata неоднозначен

Transport уже Polza AI, но audit metadata сохраняет `provider=deepseek`, поскольку модель поставляется DeepSeek. Нужно отдельно закрепить naming convention для transport provider и model provider.

### P2 — standalone workflow docs для новых компонентов неполны

Finalization и report stub теперь описаны в `ARCHITECTURE.md`, `README.md` и разделе Aggregator, но отдельные документы уровня `workflows/finalization.md` и `workflows/report-generation.md` отсутствуют. Это не мешает текущему happy path, но усложняет дальнейший support и regression review.

### P2 — Round 2 требует полного runtime regression

В текущем run Round 2 фактически сработал для `nm_price_with_vat`. В документации есть расхождение: Targeted Recheck описывает rules для всех 27 полей, а FIELD_CATALOG coverage matrix содержит более узкий historical набор. Полный per-field runtime regression не доказан одним E2E run.

### P2 — fan-out и повторные Finalization calls требуют нагрузочной проверки

Один Worker обрабатывал 16 units, а Aggregator завершался примерно за 90 секунд. Finalization вызывается несколькими независимыми ветками: это корректно с точки зрения DB synchronization, но требует проверки contention, повторных вызовов и роста числа документов.

### P2 — happy path не закрывает reliability gaps

Остаются риски по error policy, Docling deadline, unsupported documents, retry-safe units, selective AI retry и Orchestrator error handling. Успешный E2E не доказывает закрытие failure scenarios.

## 6. Что сейчас НЕ нужно менять

- не менять рабочую логику workflow только из-за найденных legacy nodes;
- не менять prompts или AI validation rules без отдельного regression dataset;
- не менять структуру PostgreSQL и не добавлять FK/checks в рамках этого review;
- не переименовывать `field_key` и не менять число 27 полей;
- не трактовать `not_found` как `false` или отрицательный факт;
- не удалять `rejected` facts из persistence layer;
- не ослаблять строгую логику `government_contract`;
- не объединять гарантию качества и обеспечение гарантийных обязательств;
- не разделять `nm_price_with_vat` без новой версии field catalog и migration plan;
- не считать report stub полноценной генерацией отчёта.

## 7. Рекомендации и следующие шаги

### Приоритет 1 — завершить report stage

Реализовать контролируемый путь: `completed run → ordered FINAL 1..27 → Markdown artifact → XLSX artifact → Telegram delivery`. Нужны idempotency, audit trail, retry policy и явный terminal status delivery.

### Приоритет 2 — regression scenarios

Проверить 26/27 и 27/27, два одновременных completion claim, повторный Finalization после `completed`, existing candidate без usable recheck context, strict `government_contract`, разделение warranty semantics, Round 2 для каждого `field_key` и report generation exactly once.

### Приоритет 3 — убрать semantic/configuration drift

Отдельно составить inventory unreachable legacy nodes, определить deprecated nodes, синхронизировать transport/model-provider naming и согласовать Round 2 coverage между `FIELD_CATALOG.md`, workflow docs и runtime tests.

### Приоритет 4 — нагрузочная и failure-проверка

Проверить много документов, большое количество units, параллельные calls, AI timeout/error, Docling terminal failure и partial document failure до изменения retry/backoff или concurrency policy.
