# FIELD_CATALOG — tender_fields_v1

**Статус:** Active development / MVP  
**Последнее обновление:** 2026-08-22  
**Версия каталога:** `tender_fields_v1`  
**Назначение:** единый semantic source of truth по 27 полям финального тендерного отчёта.

---

## 1. Зачем нужен этот документ

Этот файл фиксирует не архитектуру workflow, а **смысл каждого из 27 полей**.

Он отвечает на вопросы:

- что именно означает `field_key`;
- что должно попадать в поле;
- что нельзя считать значением этого поля;
- какой формат результата ожидается в отчёте;
- есть ли deterministic TenderMeta mapping;
- покрыто ли поле в Extractor / Round 1 / Targeted Recheck / Round 2;
- где бизнес-смысл ещё требует подтверждения.

Главная цель — чтобы одно и то же поле не трактовалось по-разному в:

```text
Document Worker / Extractor
Aggregator Round 1
TenderMeta Resolver
Targeted Recheck
Semantic Aggregator Round 2
Report generation
```

---

## 2. Иерархия источников смысла

При расхождении формулировок использовать следующий приоритет:

```text
1. Шаблон Дмитрия
   ↓
   что заказчик хочет видеть в финальном отчёте

2. Extractor FIELD_CATALOG
   ↓
   что система считает candidate fact этого поля

3. Aggregator Round 1 FIELD_RULES
   ↓
   как candidate facts должны сводиться в одно значение

4. Targeted Recheck RECHECK_PROFILES
   ↓
   как поле ищется повторно и какие semantic traps запрещены

5. Round 2 FIELD_RULES
   ↓
   как поле финально разрешается после Targeted Recheck
```

Если бизнес-смысл ещё не подтверждён, текущая реализация фиксируется как временная и поле помечается:

```text
⚠️ REQUIRES_BUSINESS_CONFIRMATION
```

До подтверждения:

- `field_key` не менять;
- количество полей 27 не менять;
- downstream contract не менять;
- менять только semantic layer после согласования.

---

## 3. Статусы

### `CURRENTLY_DEFINED`

Поле имеет достаточно согласованную текущую трактовку для MVP.

Это **не означает**, что заказчик формально утвердил каждую формулировку.

### `REQUIRES_BUSINESS_CONFIRMATION`

Есть существенная неоднозначность между:

- формулировкой в шаблоне Дмитрия;
- текущей трактовкой в системе;
- или ожидаемым форматом финального ответа.

### Тип уточнения

- `SEMANTIC` — нужно уточнить, что именно считается значением поля.
- `OUTPUT_FORMAT` — смысл понятен, но надо уточнить, как именно показывать ответ.
- `BOUNDARY` — нужно уточнить границу с соседним полем.

---

## 4. Общие правила для всех полей

1. Отсутствие найденного текста **не означает отрицательный ответ**.
2. `not_found` означает:
   > значение не удалось надёжно установить по предоставленным источникам после полного анализа.
3. Нельзя выводить `нет / не требуется / не предусмотрено` только из отсутствия упоминания.
4. `resolved` должен опираться на подтверждённый evidence или доверенный deterministic metadata mapping.
5. `requires_review` используется, когда есть релевантный кандидат, но остаётся существенная неоднозначность.
6. `field_key` не меняется без отдельного изменения версии каталога.
7. На MVP итоговое значение хранится в `value_text`, даже если поле по смыслу boolean-like.

**Название клиента:** Предмет закупки  
**Статус:** `CURRENTLY_DEFINED`

### Канонический смысл

Конкретный товар, работа или услуга, которые закупаются.

- конкретное наименование товара;

- цену;

может закрывать поле deterministic Metadata Resolver.

## 2. `nm_price_with_vat`

**Название клиента:** НМЦ (с НДС)  
**Статус:** `CURRENTLY_DEFINED`

### Канонический смысл

Начальная максимальная цена закупки/контракта и сведения об НДС, только если соответствующий смысл подтверждён источником.

### Что должно попадать

- НМЦ;
- НМЦК;
- начальная максимальная цена;
- подтверждённая информация об НДС.

### Не путать

- цену отдельной позиции;
- сумму спецификации;
- итоговую сумму, назначение которой как НМЦК не доказано.

### Критичное правило

Нельзя автоматически считать любую найденную сумму НМЦК.

Наличие/отсутствие НДС не додумывается.

### TenderMeta

В Recheck разрешён контекст:

```text
max_price
```

Но совпадение суммы с metadata само по себе не доказывает смысл НМЦК.

### Реализация

```text

```

## 11. `participation_guarantee`

**Название клиента:** БГ на участие  
**Статус:** `⚠️ REQUIRES_BUSINESS_CONFIRMATION`  
**Тип уточнения:** `SEMANTIC`

### Текущая трактовка системы

Широкая:

> обеспечение заявки на участие, включая банковскую/независимую гарантию, денежные средства и иные формы обеспечения.

### Почему требует уточнения

В шаблоне Дмитрия указано именно:

```text
БГ на участие
```

Неясно, хочет ли он:

1. только банковскую/независимую гарантию;
2. или вообще любое обеспечение заявки.

### До уточнения

Сохранять текущую более широкую трактовку.

### Safety contract до точного доказательства

Общие правила, банковские требования, сроки возврата и формулировки вида
«если предусмотрено» или «размер устанавливается в пункте …» сами по себе не
доказывают, что обеспечение заявки применимо именно к этой закупке и каков его
размер. Такой material нельзя завершать как `resolved` только по формальной
полноте candidate list.

```text
Round 1 reported resolved без proof применимости/размера
→ requires_recheck

terminal Round 2 без такого proof
→ requires_review с provisional value/evidence
```

Отсутствие proof не означает `не требуется`, `нет` или `not_found`.

### Не путать

- обеспечение исполнения договора;
- обеспечение гарантийных обязательств;
- стоимость участия.

### После подтверждения проверить

```text
Extractor FIELD_CATALOG
Round 1 FIELD_RULES
RECHECK_PROFILES
Round 2 FIELD_RULES, если поле будет добавлено
```

## 13. `delivery_term`

**Название клиента:** Срок поставки (исполнения)  
**Статус:** `⚠️ REQUIRES_BUSINESS_CONFIRMATION`  
**Тип уточнения:** `SEMANTIC`

### Текущая трактовка системы

Система специально различает:

```text
срок поставки / выполнения / оказания услуг
```

и:

```text

```

```text

```

Слово `(исполнения)` допускает более широкую трактовку.

### Вопрос для Дмитрия

Если документация содержит только общий срок исполнения договора, но отдельного срока поставки нет — считать ли общий срок значением этого поля?

### До уточнения

```text

```

### Текущая граница

`licenses_certificates`:

> документы о разрешении / соответствии / характеристиках товара, работ, услуг или поставщика.

`required_official_certificates`:

> официальные справки, выписки и подтверждения из органов/реестров о самом участнике или его статусе.

### До уточнения

Использовать эту границу.

### Safety contract полноты

`resolved` должен покрывать material обязательные официальные документы о
participant/status, а не только один их подтип. Налоговые справки не закрывают
автоматически выписки ЕГРЮЛ/ЕГРИП, реестр МСП, документы о регистрации/постановке
на учёт и иные обязательные официальные подтверждения, даже если часть материала
была извлечена в соседнее `application_documents`.

```text
Round 1 reported resolved без proof material completeness
→ requires_recheck

terminal Round 2 без такого proof
→ requires_review с provisional value/evidence
```

Это containment-only покрытие: оно сохраняет audit и не создаёт отрицательный
факт из отсутствия информации.

### Реализация

```text

```

# 8. Что менять после бизнес-уточнения

Если `field_key` остаётся прежним, архитектуру менять не нужно.

Для semantic-изменения поля проверить только соответствующие semantic layers:

```text
1. Document Worker
   Подготовить запрос для AI
   → FIELD_CATALOG.description

2. TENDER — Агрегация закупки
   Подготовить запрос Semantic Aggregator
   → FIELD_RULES

3. TENDER - Targeted Recheck
   Подготовить #2 Targeted Recheck Request
   → objective
   → search_terms
   → rules
   → metadata_keys

4. Targeted Recheck Round 2
   Подготовить запрос #2 Semantic Aggregator
   → FIELD_RULES
```

Обычно не требуется менять:

```text
field_key
PostgreSQL schema
FINAL normalizer
tender_field_final_v1
UPSERT
27-field grouping
future 27/27 readiness
```

---

# 9. Когда потребуется архитектурное изменение

Архитектура изменится, если мы решим:

- переименовать `field_key`;
- добавить новое поле;
- удалить поле;
- разделить одно поле на два.

Например:

```text
advance_contract_guarantee
```

разделить на:

```text
contract_performance_guarantee
advance_guarantee
```

Тогда потребуется новая версия каталога и изменение:

```text
27-field list
grouping
prompts
DB constraints / validation
readiness count
report
tests
```

До бизнес-подтверждения этого не делать.

# 11. Правило обновления FIELD_CATALOG

При любом изменении смысла поля:

1. сначала обновить этот документ;
2. указать, почему изменился смысл;
3. изменить semantic layer workflow;
4. выполнить regression test;
5. только потом считать изменение завершённым.

Этот документ должен оставаться главным human-readable semantic source of truth для `tender_fields_v1`.
