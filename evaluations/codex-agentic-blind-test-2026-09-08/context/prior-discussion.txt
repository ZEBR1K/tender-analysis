Пример с датами

1. Обеспечение исполнения договора
2. Обеспечение возврата аванса

- не использованы ли запрещённые candidates;
- соответствует ли JSON схеме.

Это фундаментальная проблема LLM-суммаризации:
много evidence
→ один короткий свободный текст
→ нет детерминированного контроля покрытия каждого обязательного пункта

Наш Validator в основном отвечает на вопрос:
Подтверждается ли написанный моделью текст предоставленными цитатами?

Но это не то же самое, что:
Нашла ли модель всё существенное и правильно ли связала каждый фрагмент с нужным полем?

Если модель написала только правдивую половину ответа, Validator может подтвердить её. Он не знает, что вторая половина была обязательна, если мы не дали ему отдельный checklist покрытия.
Кроме того, Validator не способен найти то, чего вообще нет в его входных данных. Если Worker потерял связь:
заголовок раздела → дата
переключатель → подпись
условие → обязательный документ
то Validator получает уже повреждённую картину.

Workflow-модель	Codex-ревьюер
Один ограниченный этап	Вся цепочка
Отфильтрованные candidates	Candidates + raw documents
Жёсткий prompt одного поля	Может сопоставлять несколько полей
Ограниченный контекст	Источники и контракт рядом
Должна выдать структурированный ответ	Может остановиться и исследовать противоречие
Проверяется главным образом grounding	Проверяет ещё полноту и межполевую согласованность


Поэтому правильная цель — не сделать модель «такой же умной, как Codex», а перенести найденные Codex проверки в детерминированные контракты workflow.
Например:

Коротко: сейчас workflow хорошо проверяет, что модель не выдумала написанное, но ещё недостаточно хорошо проверяет, что она правильно поняла структуру и ничего существенного не потеряла. Codex обнаруживает ошибки именно на этом втором уровне.

Схема будет такой:
n8n
│
├─ загружает и регистрирует документы
├─ получает Docling/OCR
├─ извлекает ActiveX
├─ сохраняет semantic blocks
│
└─ POST /analysis-jobs
       ↓
   codex-runner
       ├─ создаёт изолированную папку запуска
       ├─ получает документы и FIELD_CATALOG
       ├─ запускает codex exec
       ├─ проверяет JSON
       └─ возвращает 27 результатов
               ↓
          n8n сохраняет FINAL
               ↓
          Finalization → PDF
Официально codex exec предназначен именно для запуска Codex из скриптов и автоматических pipeline. Он поддерживает неинтерактивный режим, JSONL и финальный ответ по заданной JSON Schema. Документация Codex non-interactive mode.
Как будет выглядеть вызов
Внутри отдельного контейнера примерно так:
codex exec \
  --ephemeral \
  --sandbox read-only \
  --output-schema tender-field-results.schema.json \
  -o final-results.json \
  - < analysis-prompt.txt
Codex получает доступ только к рабочей папке конкретной закупки:
/jobs/<analysis_run_id>/
├── AGENTS.md
├── task.md
├── FIELD_CATALOG.md
├── tender-meta.json
├── semantic-blocks.jsonl
├── activex-option-states.json
├── documents/
└── tender-field-results.schema.json
В task.md будет написано:

Прямой вариант тоже возможен:
n8n Execute Command → codex exec
Но он хрупкий:
- Codex должен быть установлен внутри контейнера n8n;
- длительный процесс удерживает execution;
- перезапуск контейнера оборвёт анализ;
- сложнее задавать timeout и повторные попытки;
- сложнее ограничить доступ к файлам;
- stdout/stderr могут оказаться большими;
- обновление Codex CLI будет связано с обновлением n8n-контейнера.

n8n HTTP Request → codex-runner

  }
}

Codex:

n8n:
проверяет JSON → сохраняет → финализирует → создаёт отчёт

- цитата присутствует в указанном semantic block;
- для составных полей закрыты все обязательные части;
- resolved запрещён при незакрытом material clause.
То есть мы не будем слепо доверять Codex.

Да. gpt-5.3-codex доступен через OpenAI API, поддерживает Responses API, Structured Outputs и function calling. Официальная карточка модели.
Можно сделать:
Extractor:
GLM 5.3 Flash → gpt-5.3-codex

Validator:
Gemini 3.7 Flash → gpt-5.3-codex

Semantic Aggregator:
Gemini/GLM → gpt-5.3-codex
И передавать каждой ноде строгую json_schema.
Технически потребуется:
- вместо OpenRouter вызвать OpenAI Responses API;
- привязать OpenAI credential;
- указать model: gpt-5.3-codex;
- передать текущую JSON Schema через Structured Outputs;
- адаптировать разбор ответа, потому что формат Responses API отличается;
- сохранить существующие deterministic checkers.
Но простая замена модели не даст «того самого Codex»
Если оставить архитектуру:
один analysis unit
→ один Extractor
→ короткий Validator context
→ отфильтрованные candidates
то даже сильная Codex-модель продолжит видеть ограниченный кусок документа. Она может работать лучше GLM, но всё равно не увидит общей картины.
Например, если Extractor передаст:
16 сентября → application_deadline
Validator не обязательно узнает, что в соседнем разделе это была дата рассмотрения. У него может не быть соседнего заголовка.
Поэтому существуют два разных эксперимента.
Вариант 1 — минимальная замена
Текущий workflow
+
gpt-5.3-codex вместо GLM/Gemini
+
строгие JSON Schema
Плюсы:
- небольшое изменение;
- сохраняется текущая архитектура;
- можно быстро прогнать A/B;
- результат сразу совместим с БД.
Минус: сохраняются все проблемы раннего разрезания контекста.
Вариант 2 — полноценный Codex-анализ
Docling/OCR/ActiveX
→ весь комплект данных одной закупки
→ Codex agent
→ 27 полей
→ deterministic validation
→ Finalization
Именно второй вариант ближе к тому, как Codex сейчас обнаружил ошибки.
Что я считаю правильным
Не заменять вслепую все модели сразу. Сделать два независимых теста на той же закупке:
A. Текущая архитектура + gpt-5.3-codex во всех трёх ролях
B. Один агентный Codex-анализ всей закупки
Оба варианта должны работать вслепую, не видя существующий отчёт. Потом сравниваем:
- даты;
- ActiveX-поля;
- банковские гарантии;
- стоимость участия;
- национальный режим;
- справки;
- полный состав заявки;
- число false_resolved;
- число false_not_found;
- стоимость и время выполнения.
Мой прогноз: простая замена моделей улучшит качество, но агентный вариант окажется точнее на междокументных, конфликтных и составных полях.
То есть ответ: да, Codex-модель можно прямо поставить вместо текущих API-моделей. Но наиболее ценное преимущество мы получим, если заменим не только название модели, а сам узкий одношаговый вызов на агентный анализ всей закупки.
